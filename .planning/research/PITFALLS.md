# Domain Pitfalls

**Domain:** Browser Pre-Scraping Tooling (Selector-First LLM Workflow)
**Researched:** 2025-02-09
**Confidence:** MEDIUM-HIGH (based on multiple industry sources, verified patterns)

## Critical Pitfalls

Mistakes that cause rewrites or major issues.

---

### Pitfall 1: The Selector Fragility Trap

**What goes wrong:**
Hand-crafted CSS/XPath selectors break silently when websites redesign. A scraper that worked yesterday returns empty or partial data today without errors. This is the #1 maintenance burden in scraping—the "works on my machine" nightmare that doesn't surface until data consumers notice gaps.

**Why it happens:**
- Selectors tied to DOM structure (e.g., `div[3]/table/tr[2]`) are inherently brittle
- Class names and IDs auto-generated by frameworks (React, Vue) change on every build
- Marketing teams redesign pages without considering scrapers
- A/B testing creates multiple page variants

**Consequences:**
- Data pipelines silently produce incomplete data for days/weeks
- Selectors need constant manual updating across hundreds of pages
- ML models trained on scraped data become unreliable

**Prevention:**
1. **Prefer semantic selectors** over positional ones—use `data-testid` attributes, ARIA labels, or content-based matching
2. **Validate selector results** immediately—assert expected data presence, not just element presence
3. **Design for selector regeneration**—build LLM-driven rediscovery workflows into your architecture
4. **Use multiple selector strategies** per data point and fall back gracefully
5. **Avoid CDP-dependent selector introspection**—it increases detection surface

**Warning signs:**
- Selectors longer than 30 characters or with many nested indices
- Scrapers returning "success" but with null/empty data fields
- Higher-than-expected variance in data completeness over time
- Selectors referencing auto-generated class names (e.g., `._3xKp8`)

**Phase to address:**
Phase 2 (Selector Discovery Core)—design the LLM selector discovery to output *multiple* candidate selectors per data point with confidence scores, and include validation hooks.

### Pitfall 2: The Implicit Wait Disaster

**What goes wrong:**
Scrapers use fixed `waitForTimeout()` calls to wait for dynamic content. Tests pass locally but fail intermittently in production due to network variance, or waste time waiting unnecessarily.

**Why it happens:**
- "It works with 2-second delay on my laptop"
- Not understanding the difference between page load and data availability
- AJAX calls completing after DOM ready events
- Animation delays making elements technically present but not interactable

**Consequences:**
- Flaky, unreliable scraping that fails unpredictably
- Excessive wait times wasting resources and increasing detection risk
- Race conditions causing "element not found" errors
- Impossible to run at scale efficiently

**Prevention:**
1. **Never use fixed timeouts**—always wait for explicit conditions
2. **Wait for network idle** when content depends on XHR/fetch
3. **Wait for element state** (visible, enabled) not just presence
4. **Use selector-based auto-waits** built into modern automation tools
5. **Implement smart retry logic** with exponential backoff

**Warning signs:**
- `waitForTimeout(2000)` scattered throughout codebase
- "Works locally but fails in CI"
- Inconsistent failure rates across different environments
- Elements found but interactions failing

**Phase to address:**
Phase 1 (Navigation & Wait Primitives)—design wait tools around conditions, not durations. Provide `wait_for_element`, `wait_for_network_idle`, `wait_for_selector_state`.

### Pitfall 3: The Browser Resource Explosion

**What goes wrong:**
Long-running scraping processes leak memory or accumulate browser contexts/pages without cleanup, eventually crashing with OOM errors or grinding to a halt.

**Why it happens:**
- Treating browsers as "just another library" instead of resource-heavy processes
- Not closing pages/contexts after use
- Singleton browser instances holding references to detached DOM
- Chrome flags not optimized for headless operation
- Accumulating browser instances in loops without rate limiting

**Consequences:**
- Production crashes at 3am requiring manual intervention
- Need for expensive infrastructure to handle "leaky" resource usage
- Cascading failures when scraper restarts lose in-progress work
- Debugging nightmares because heap dumps show detached DOM trees retained by JS references

**Prevention:**
1. **Always close contexts/pages in finally blocks** or use `using` patterns
2. **Set explicit memory limits** via `--max_old_space_size`
3. **Use browser contexts** (lighter) instead of new browser instances where possible
4. **Implement circuit breakers** to restart browsers after N operations
5. **Monitor heap usage** and alert on growth trends
6. **Apply Chrome flags for headless stability:**
   ```
   --no-sandbox --disable-gpu --disable-dev-shm-usage
   --disable-extensions --disable-background-networking
   --memory-pressure-off
   ```

**Warning signs:**
- Gradually increasing memory usage over hours
- OOM crashes after consistent operation time
- "Error: Protocol error (Target.createTarget): Target closed" errors
- Slower execution over time without code changes

**Phase to address:**
Phase 1 (Infrastructure Setup)—design browser lifecycle management from day one. Each tool call should handle resource cleanup even on failure.

### Pitfall 4: The Anti-Bot Detection Arms Race Blindness

**What goes wrong:**
Scrapers work briefly then get blocked, rate-limited, or served CAPTCHAs. Teams add proxies and headers reactively without understanding the detection mechanisms.

**Why it happens:**
- Assuming "headless" means "undetectable"
- Using default user agents and headers
- Predictable request timing patterns
- Fingerprint inconsistencies (WebGL, Canvas, fonts don't match UA)
- CDP/Playwright detection via `navigator.webdriver` or Chrome DevTools Protocol signatures
- Lack of proxy rotation or using cheap/shared proxies already blacklisted

**Consequences:**
- Complete data pipeline failure
- IP ranges permanently blocked
- Legal threats from aggressive targets
- Reactive "whack-a-mole" development instead of proactive design

**Prevention:**
1. **Avoid CDP-based tooling** for core features—it increases detection surface (per project constraints)
2. **Implement request spacing** with randomization to avoid pattern detection
3. **Use high-quality residential/mobile proxies** for production workloads
4. **Handle failures gracefully**—don't retry aggressively when blocked
5. **Monitor for block indicators** (CAPTCHA keywords, 403/429 status codes)
6. **Use stealth plugins** (puppeteer-extra-stealth) if using Puppeteer-based solutions

**Warning signs:**
- Success rate degrading over time
- Unexpected redirect chains to login/CAPTCHA pages
- Response content shorter than expected (blocked page HTML)
- HTTP status codes shifting to 403/429/503

**Phase to address:**
Phase 4 (Scaling & Reliability)—detection countermeasures are deferred initially per project scope, but architecture should support proxy injection and header customization.

### Pitfall 5: The "Silent Success" Data Validation Gap

**What goes wrong:**
Scrapers return "success" status but the extracted data is null, malformed, or from the wrong page state. Data consumers don't realize they're working with garbage until downstream analysis fails.

**Why it happens:**
- Validating HTTP status codes but not data schema
- Selectors matching different elements after site changes
- JavaScript errors causing partial page load
- Race conditions extracting data before it's ready
- Not validating extracted data against expected formats

**Consequences:**
- ML models trained on garbage data
- Business decisions based on incomplete datasets
- Silent data corruption in analytics pipelines
- Loss of trust in scraping infrastructure

**Prevention:**
1. **Schema validation on every extraction**—assert expected fields exist and have valid types
2. **Content fingerprinting**—hash known-good page states and compare
3. **Data completeness checks**—assert minimum data density thresholds
4. **Snapshot validation**—validate that key structural elements exist before extraction
5. **Log null/missing fields** with URLs for debugging

**Warning signs:**
- Scrapers completing "successfully" with 0% data extraction
- Gradual decrease in data field completeness over time
- Null values increasing in historical data
- Data variance that doesn't match site behavior

**Phase to address:**
Phase 2 (Selector Discovery Core)—every selector should include validation rules: expected element count, content patterns, and fallback selectors.

### Pitfall 6: The LLM Token Explosion

**What goes wrong:**
Sending full page HTML to LLMs for selector discovery consumes excessive tokens, becomes cost-prohibitive, and hits context window limits.

**Why it happens:**
- Modern web pages are 2-5MB of HTML with inline scripts, styles, ads
- LLM costs scale with token count (roughly $0.01-0.03 per 1K tokens)
- Sending raw HTML without preprocessing
- Not understanding which page elements are relevant to extraction goals

**Consequences:**
- API costs 10-100x higher than necessary
- Hitting context limits (128K tokens) on moderately complex pages
- Slow selector discovery making the workflow impractical
- Truncated context causing poor selector quality

**Prevention:**
1. **Pre-process HTML before LLM analysis**—remove scripts, styles, comments, ads
2. **Semantic compression**—extract just the DOM structure without content noise
3. **Chunk large pages**—process by section when full page exceeds limits
4. **Use smaller/faster models** for initial pass (Claude Haiku, GPT-3.5)
5. **Cache processed representations**—avoid re-processing identical page structures

**Warning signs:**
- API costs exceeding $0.10 per page analyzed
- Context window exceeded errors
- Slow response times (>30s) for selector discovery
- Truncated responses from LLM

**Phase to address:**
Phase 2 (Selector Discovery Core)—HTML preprocessing and intelligent chunking should be built into the discovery pipeline.

## Technical Debt Patterns

Shortcuts that seem reasonable but create long-term problems.

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Single hard-coded selector per field | Faster implementation | Brittle, breaks constantly | Never in production—always have fallbacks |
| Fixed wait times (sleep) | Works locally | Flaky in production, wastes time | Only in local debugging, never committed |
| No schema validation | Faster iteration | Silent data corruption | Only during initial prototyping |
| Browser instances per request | Simpler code | Resource exhaustion, OOM crashes | Never—use contexts or connection pooling |
| Skip error handling | Faster MVP | Cascading failures, lost work | Never—handle errors at tool boundaries |
| No request spacing | Faster execution | Detection and blocking | Never—implement rate limiting from day 1 |
| Full HTML to LLM | Simpler processing | Token explosion, high costs | Only for small static pages |

## Integration Gotchas

Common mistakes when connecting to external services.

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| MCP Server | Not handling tool call timeouts | Set explicit timeouts, implement cancellation tokens |
| Browser WebSocket | No reconnection logic | Implement exponential backoff reconnect |
| LLM API | No retry on rate limits | Handle 429s with exponential backoff, track token usage |
| Proxy Services | Using shared/datacenter proxies | Use residential/mobile proxies for production |
| Page Snapshots | Sending raw HTML without preprocessing | Strip scripts/styles, compress to semantic structure |

## Performance Traps

Patterns that work at small scale but fail as usage grows.

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| New browser per page | Linear resource growth, OOM at ~50 concurrent | Use browser contexts (1:100 cost reduction) | >10 pages concurrently |
| Synchronous sequential scraping | Predictable but slow | Implement concurrency with semaphores | >100 pages/hour |
| No caching of static resources | Bandwidth explosion, slow loads | Implement request interception and caching | >1000 pages/day |
| Full page screenshots for debugging | Storage explosion, slow operations | Use element-only screenshots, conditional capture | >100 pages/debug session |
| Real-time selector discovery on every scrape | API cost explosion, slow pipelines | Cache selectors, schedule rediscovery | >10 scrapes per target |

## Security Mistakes

Domain-specific security issues beyond general web security.

| Mistake | Risk | Prevention |
|---------|------|------------|
| Arbitrary code execution in browser | XSS, credential theft, SSRF | Explicitly exclude `run_code` tools from v1 (per constraints) |
| No proxy for outbound requests | IP exposure, rate limiting | Proxy all traffic through managed service |
| Storing scraped credentials | Data breach liability | Never store auth tokens from scraped sessions |
| Replay of captured requests | Unauthorized actions | Sanitize headers, exclude cookies from logged snapshots |
| LLM prompt injection via page content | Malicious selectors, data exfiltration | Sanitize HTML before LLM processing, validate outputs |

## UX Pitfalls

Common user experience mistakes in this domain.

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Opaque error messages | "Something went wrong" doesn't help debug | Include selector tried, page state, network status |
| No progress visibility | Users wait blindly for long operations | Stream progress updates during multi-step workflows |
| Success without data verification | User thinks extraction worked | Show preview of extracted data, highlight missing fields |
| Manual selector editing without testing | Selectors break in production | Provide live test-before-save workflow |
| No selector versioning | Can't rollback when site changes | Store selector history, support rollback |

## "Looks Done But Isn't" Checklist

Things that appear complete but are missing critical pieces.

- [ ] **Selector discovery:** Missing fallback strategies—verify multiple selectors returned per field
- [ ] **Wait primitives:** Only implementing fixed waits—verify condition-based waits for network/element state
- [ ] **Error handling:** Catching errors but not recovering—verify graceful degradation with partial data
- [ ] **Resource cleanup:** Closing browsers but not contexts/pages—verify all resources disposed in finally blocks
- [ ] **Data validation:** Checking status codes but not content—verify schema validation on every extraction
- [ ] **Rate limiting:** Implemented per-scrape but not globally—verify distributed rate limiting for concurrent usage
- [ ] **LLM preprocessing:** Sending raw HTML—verify HTML cleaning and compression before LLM calls
- [ ] **Detection handling:** Ignoring 403s and CAPTCHAs—verify detection indicators are logged and alerted
- [ ] **Selector maintenance:** Manual only—verify scheduled rediscovery and health checks
- [ ] **Testing:** Unit tests only—verify integration tests with real browser instances

## Recovery Strategies

When pitfalls occur despite prevention, how to recover.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Selector breakage | LOW-MEDIUM | Rediscover selectors via LLM, update selector registry |
| Memory leak/OOM crash | MEDIUM | Restart browser pool, implement circuit breaker pattern |
| IP blocking | LOW-MEDIUM | Rotate proxies, implement backoff, verify with health checks |
| Silent data corruption | HIGH | Re-scrape historical data, audit data pipeline, add validation |
| LLM token explosion | LOW | Implement preprocessing, switch to cheaper model for initial pass |
| Detection escalation | HIGH | Pause scraping, analyze detection vectors, implement stealth measures |
